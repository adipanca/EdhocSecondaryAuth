% Abstract (single paragraph, about 200 words, no blank lines)
\abstract{5G secondary authentication lets an external data network (DN) authenticate user equipment (UE) through the Extensible Authentication Protocol (EAP), but widely used methods such as EAP-TLS exchange certificate chains over many EAP round-trips and rely on elliptic-curve cryptography that a quantum adversary can break. Moving to post-quantum key encapsulation also breaks the role symmetry of authenticated key exchange, because a key encapsulation mechanism (KEM) implicitly authenticates only the decapsulating party. We propose a role-symmetric hybrid post-quantum EAP-EDHOC (Ephemeral Diffie--Hellman Over COSE) protocol that restores this symmetry: the UE and the DN authentication server each receive exactly one X-Wing (X25519 + ML-KEM-768) encapsulation to a one-time static key, each authenticate with a detached ML-DSA-44 signature, and each rotate and erase their key after every run. The mirrored rotation gives both parties forward secrecy and post-compromise security, and the independent signatures give Key-Compromise Impersonation (KCI) resistance in both directions. The exported Extended Master Session Key bootstraps application-layer keys for login-free server access. We model nine security requirements in ProVerif for seven methods, including a negative control without key erasure. An implementation on Open5GS, UERANSIM, and FreeRADIUS, run through the full 5G core path, shows that the symmetry extends to the traffic: of the $12{,}259$-byte handshake, the UE sends $6{,}146$ bytes and the server $6{,}113$ bytes. The cost, in contrast, is asymmetric and lies in transport fragmentation rather than in cryptography: the proposal computes slightly more than hybrid EAP-TLS but needs half its EAP round-trips.}

\section{Introduction}
\label{sec1}

Primary authentication through 5G Authentication and Key Agreement (5G-AKA) or EAP-AKA$'$ proves only that a subscriber is legitimate for the operator, not that it may use the services of an external data network~\cite{TS33501,TS23501}, and formal analyses of 5G-AKA have exposed protocol weaknesses~\cite{Edris20} and a privacy attack carried over from 4G~\cite{Borgaonkar19}. 5G therefore defines \emph{secondary authentication} based on the Extensible Authentication Protocol (EAP)~\cite{RFC3748,TS33501}, in which the user equipment (UE) authenticates to a data network (DN) Authentication, Authorization, and Accounting (DN-AAA) server of the service provider; it has drawn dedicated UE--DN frameworks~\cite{Gong20} and analyses of the EAP-TLS profile~\cite{RFC5216,TS33501}. Figure~\ref{fig:proto-overall} shows the flow: after primary authentication between the Access and Mobility Management Function (AMF) and the Authentication Server Function (AUSF), and slice selection through the Network Slice Selection Function (NSSF) and the Network Repository Function (NRF), the UE runs secondary authentication with the DN-AAA over the Session Management Function (SMF)/User Plane Function (UPF) path, and the DN-AAA bootstraps keys from the Extended Master Session Key (EMSK) toward an application server (AS), which the UE then reaches without a further login.

EAP-TLS (Transport Layer Security)~\cite{RFC5216,RFC9190} over TLS~1.3~\cite{RFC9846} exchanges X.509 certificate chains that add bytes and EAP round-trips on the links of constrained Internet of Things (IoT) and industrial devices. EDHOC (Ephemeral Diffie--Hellman Over COSE)~\cite{RFC9528,RFC9529}, a compact key exchange based on the Concise Binary Object Representation (CBOR) and CBOR Object Signing and Encryption (COSE), is carried in EAP by EAP-EDHOC~\cite{EAPEDHOC} and is markedly more efficient than Datagram TLS (DTLS)~1.3~\cite{FVW24,PSM+24}, but its elliptic-curve Diffie--Hellman falls to Shor's algorithm~\cite{shor1994algorithms} and to \emph{harvest-now, decrypt-later} attacks. Hybrid post-quantum cryptography (PQC) is the recommended transition path~\cite{NIST,Migration,ANSSI,PQUIP,BBF+19}, and X-Wing~\cite{XWing,XWingDraft} is a compact hybrid key encapsulation mechanism (KEM) that combines X25519 with ML-KEM-768. Hybrid-PQC EAP-EDHOC in a real 5G system, and the effect of PQC payloads on Remote Authentication Dial-In User Service (RADIUS) encapsulation~\cite{RFC2865,RFC3579}, remain largely unexplored~\cite{FTK+25,fraile2025reinventing,pocero,SIK+25}.

\textbf{Symmetry perspective.} Replacing Diffie--Hellman with a KEM breaks the role symmetry of key exchange: both Diffie--Hellman parties contribute a share, but a KEM implicitly authenticates only the decapsulator, and EDHOC's methods already mix symmetric (SIG-SIG, STAT-STAT) and mirror-image (SIG-STAT, STAT-SIG) role assignments. Our design restores the symmetry explicitly: each party receives exactly one X-Wing encapsulation to a one-time static key, is authenticated by its own detached ML-DSA-44 signature, and rotates its static key after every run, which replaces the ephemeral key pair as the source of forward secrecy. The protocol's \emph{costs}, by contrast, are strongly asymmetric: cheap in computation and expensive in transport.

The contributions of this work are as follows:
\begin{enumerate}
\item A role-symmetric hybrid PQC EAP-EDHOC protocol for 5G secondary authentication, built on X-Wing with a Key-Compromise Impersonation (KCI)-resistant detached ML-DSA-44 signature gate and a symmetric rotation of one-time static keys that gives forward secrecy and post-compromise security without an ephemeral key pair.
\item A ProVerif~\cite{blanchet2001proverif,blanchet2016automated} analysis of nine security requirements across the proposal, the four classical EDHOC methods, and two EAP-TLS baselines, with a negative control showing that forward secrecy rests on key erasure.
\item An implementation on Open5GS~\cite{Open5GS}, UERANSIM~\cite{UERANSIM}, and FreeRADIUS~\cite{FreeRADIUS} with open-source code~\cite{ProVerifSrc}, run through the full 5G core path, including EMSK-based key bootstrapping of Object Security for Constrained RESTful Environments (OSCORE) for login-free application-server access.
\item A performance evaluation of computation, communication, EAP/RADIUS fragmentation, and packet loss that quantifies the asymmetry between cryptographic and transport cost.
\end{enumerate}

\section{Related Work}
\label{sec:relatedwork}

\textbf{Security analysis of classical EDHOC.} RFC~9528 has been analysed symbolically by Jacomme et al.~\cite{JKK+23} (all four methods), Norrman et al.~\cite{NSB21}, and Kim et al.~\cite{KDL+21}, and computationally by G\"unther and Mukendi~\cite{GM23}, Cremers et al.~\cite{CDM24}, Cottier and Pointcheval~\cite{CP22}, and Ferreira~\cite{Fer24}; P\'erez et al.~\cite{PSM+24} survey this work. A recurring finding is that the MAC-based methods (T1--T3) are vulnerable to KCI once the static Diffie--Hellman key leaks~\cite{GM23,CDM24}. These works analyse EDHOC as specified, which remains purely classical.

\textbf{Post-quantum and hybrid EDHOC.} Fraile et al.~\cite{FTK+25} propose PQ-EDHOC, a fully post-quantum variant using NIST KEMs and signatures, evaluated with microbenchmarks on constrained hardware. A companion work~\cite{fraile2025reinventing} and IETF draft~\cite{pocero} add a signature-free, KEM-based authentication method. Shin et al.~\cite{SIK+25} embed an ephemeral PQC KEM into EDHOC and omit the optional Message~4, and in follow-up work~\cite{SIK+26} they strengthen this hybrid EDHOC design toward post-quantum security against KCI. The present paper builds on that line of work and further hardens KCI resistance with a detached ML-DSA-44 gate that is independent of the KEM static keys. None of these proposals target 5G secondary authentication or integrate with EAP/RADIUS, and none combines KCI resistance with post-compromise key rotation.

\textbf{5G secondary authentication.} Gong et al.~\cite{Gong20} propose new network functions for UE--DN mutual authentication, and the EAP-TLS profile of TS~33.501 Annex~B has been formally analysed~\cite{RFC5216,TS33501}. These works do not consider PQC or the EAP-over-RADIUS fragmentation that, as we show in Section~\ref{sec:performance}, becomes the bottleneck once PQC payloads are introduced. No prior work combines hybrid PQC, a KCI-resistant gate independent of the KEM static key, formal verification, a live 5G implementation, and EMSK-based key bootstrapping.

Table~\ref{tab:methodmatrix} classifies the seven evaluated methods by the mechanism that authenticates each party. Read row by row, it exposes the role symmetry of each design: Method~0 (SIG-SIG) and Method~3 (STAT-STAT) are role-symmetric, while Methods~1 and~2 are mirror images of each other, each authenticating one party by signature and the other by a static-DH MAC. The static-DH MAC is the mechanism shown to be KCI-vulnerable~\cite{GM23,CDM24}. EAP-TLS is role-symmetric, with entity authentication provided by the \texttt{CertificateVerify} signature; its HMAC \texttt{Finished} message is a universal key-confirmation step rather than a separate authentication mechanism. Only three methods are post-quantum, and only the proposed method pairs role symmetry with a signature that is both post-quantum and detached from the key-exchange static key. Although the proposal and EAP-TLS Hybrid PQC share the same primitives, they differ in how authentication is framed, which Section~\ref{sec:performance} shows matters more for latency than the primitives themselves.

\section{Preliminaries}
\label{sec:preliminaries}

\subsection{5G Secondary Authentication}
\label{sec:prelim-secondary-auth}
EAP~\cite{RFC3748} defines three roles: the \emph{peer} (the UE), the \emph{authenticator}, which relays messages without understanding the method (the SMF), and the \emph{EAP server}, which runs the method and decides (the DN-AAA)~\cite{TS33501,TS23501}. EAP frames travel over the SMF--UPF--DN-AAA path of Figure~\ref{fig:proto-overall} and are carried in RADIUS between the SMF and the DN-AAA~\cite{RFC2865,RFC3579}. Unlike primary authentication, which the AUSF terminates inside the operator's domain, secondary authentication is terminated by a DN-AAA that the operator does not control and runs during PDU session establishment, before the session is accepted~\cite{TS33501,TS23502}. A successful method exports the Master Session Key (MSK) and the Extended MSK (EMSK)~\cite{RFC3748,RFC5295}. The MSK protects the UE--DN session; the EMSK never leaves the peer and the server and serves as a root for cryptographically separated keys through RFC~5295's Usage-Specific Root Keys (USRK). We use it to bootstrap an OSCORE~\cite{RFC8613} context with an application server without any further login.

\subsection{X-Wing Hybrid KEM}
\label{sec:prelim-xwing}
X-Wing~\cite{XWing,XWingDraft} combines X25519 with ML-KEM-768 (FIPS~203)~\cite{FIPS203,CRYSTALS} and stays secure as long as \emph{at least one} component is unbroken~\cite{PQUIP,BBF+19,TS103744}. Algorithm~\ref{alg:xwing} gives its operations: the public key $ek_{\mathrm{PQ}}\,\|\,pk_X$ has $1184+32$ bytes, and encapsulation merges the ML-KEM and ephemeral X25519 secrets with a SHA3-256 combiner that also binds both public shares, which blocks re-encapsulation and mismatch attacks~\cite{CDM24,ADH+22}. Our implementation follows the specification~\cite{XWingDraft} exactly and reproduces all of its test vectors; as permitted for a key that never leaves its device, each party stores the expanded secret key and takes $pk_X$ from its own public key during decapsulation. X-Wing is IND-CCA secure under weaker assumptions than generic combiners~\cite{XWing}. Unlike the negotiated combiners of hybrid TLS~1.3~\cite{TLS,RFC10024}, IKEv2~\cite{RFC9370}, or composite ML-KEM~\cite{LAMPS,BBF+19}, it is a fixed instantiation, like PQXDH~\cite{PQXDH,FG24} and post-quantum Noise~\cite{ADH+22}, and compact enough for COSE/CBOR. Like any KEM, it implicitly authenticates only the decapsulator; Section~\ref{sec:symmetry} shows how the protocol compensates.

\begin{algorithm}[H]
\caption{X-Wing hybrid KEM: $\mathsf{KeyGen}()$, $\mathsf{Encaps}(pk)$, and $\mathsf{Decaps}(ct, sk)$}
\label{alg:xwing}
\label{alg:xwing-keygen}\label{alg:xwing-encaps}\label{alg:xwing-decaps}
{\footnotesize
\begin{algorithmic}[1]
\State \textbf{KeyGen():}
\State \hspace{1em}$seed \gets \mathsf{random}(32)$;\ \ $(d, z, sk_{X}) \gets \mathsf{SHAKE256}(seed, 96)$
\State \hspace{1em}$(dk_{\mathrm{PQ}}, ek_{\mathrm{PQ}}) \gets \mathsf{ML\text{-}KEM\text{-}768.KeyGen\_internal}(d, z)$;\ \ $pk_{X} \gets \Xtwofive(sk_{X}, \mathsf{base})$
\State \hspace{1em}\Return $pk \gets ek_{\mathrm{PQ}} \,\|\, pk_{X}$ \ ($1184 + 32 = 1216$ bytes),\ \ $sk \gets dk_{\mathrm{PQ}} \,\|\, sk_{X}$
\State \textbf{Encaps($pk = ek_{\mathrm{PQ}} \,\|\, pk_{X}$):}
\State \hspace{1em}$(ss_{\mathrm{PQ}}, ct_{\mathrm{PQ}}) \gets \mathsf{ML\text{-}KEM\text{-}768.Encaps}(ek_{\mathrm{PQ}})$;\ \ $(sk_{e}, pk_{e}) \gets \Xtwofive.\mathsf{KeyGen}()$
\State \hspace{1em}$ss_{X} \gets \Xtwofive(sk_{e}, pk_{X})$
\State \hspace{1em}$ss \gets \mathsf{SHA3\text{-}256}\big(ss_{\mathrm{PQ}} \,\|\, ss_{X} \,\|\, pk_{e} \,\|\, pk_{X} \,\|\, \texttt{label}_{\text{X-Wing}}\big)$ \Comment{combiner}
\State \hspace{1em}\Return $(ss,\ ct \gets ct_{\mathrm{PQ}} \,\|\, pk_{e})$
\State \textbf{Decaps($ct = ct_{\mathrm{PQ}} \,\|\, pk_{e}$, $sk = dk_{\mathrm{PQ}} \,\|\, sk_{X}$):}
\State \hspace{1em}$ss_{\mathrm{PQ}} \gets \mathsf{ML\text{-}KEM\text{-}768.Decaps}(ct_{\mathrm{PQ}}, dk_{\mathrm{PQ}})$;\ \ $ss_{X} \gets \Xtwofive(sk_{X}, pk_{e})$
\State \hspace{1em}\Return $ss \gets \mathsf{SHA3\text{-}256}\big(ss_{\mathrm{PQ}} \,\|\, ss_{X} \,\|\, pk_{e} \,\|\, pk_{X} \,\|\, \texttt{label}_{\text{X-Wing}}\big)$
\end{algorithmic}
}
\end{algorithm}

\section{Proposed EAP-EDHOC Hybrid PQC Protocol}
\label{sec:eapedhocPQC}

\subsection{Assumptions and Design Rationale}
In a provisioning phase (Algorithm~\ref{alg:longterm-keygen}), the UE (Initiator) and the DN-AAA (Responder) each generate an X-Wing key pair and an ML-DSA-44 signing key and hold the peer's X-Wing public key; the verification keys $VK_R$ and $VK_I$ travel in \texttt{Plaintext2}/\texttt{Plaintext3}, bound to the transcript by the signatures. Messages are carried over EAP~\cite{RFC3748} and RADIUS~\cite{RFC2865,RFC3579} between the pass-through authenticator (SMF/UPF) and the DN-AAA~\cite{TS33501}, and a Dolev--Yao adversary~\cite{DolevYao1983} controls the network. The X-Wing static keys are \emph{one-time} keys: each party announces its next public key early, the UE in $\mathit{EAD}_1$ and the DN-AAA in $\mathit{EAD}_2$, bound to the transcript and covered by the signatures, and switches to it, erasing the old secret key, once the run completes. The DN-AAA keeps one record per UE, $(sk_{\mathsf{B}}, pk_{\mathsf{B}}, pk_{\mathsf{A}}, VK_I)$, selected by $\mathit{KeyID}_{\mathsf{B}} = H(pk_{\mathsf{B}})$, which \texttt{Message1} carries in the clear, so the outer EAP identity can be an anonymous NAI~\cite{RFC7542}; each party keeps its keys in a two-slot file written with one \texttt{fdatasync}. Authentication follows the sign-and-MAC principle of SIGMA~\cite{Kra03}, although not the SIGMA-I flow, since $\mathit{ID\_CRED}_I$ travels in \texttt{Message1} under the Responder's one-time key: X-Wing provides confidentiality and key agreement, and detached ML-DSA-44 signatures~\cite{FIPS204}, independent of the KEM keys, are the sole source of entity authentication, which closes the KCI gap of a MAC-only Method~4 variant~\cite{GM23,CDM24}. We choose ML-DSA-44 (NIST category~2) over ML-DSA-65 to limit fragmentation ($1312$-byte key, $2420$-byte signature), a deliberate size/security trade-off below the category-3 strength of ML-KEM-768.

\begin{algorithm}[H]
\caption{Long-term key generation (provisioning)}
\label{alg:longterm-keygen}
{\footnotesize
\begin{algorithmic}[1]
\State \textbf{At UE:}\ \ $(sk_{\mathsf{A}}, pk_{\mathsf{A}}) \gets \XWING.\mathsf{KeyGen}()$;\ \ $(sk_{\mathsf{SIG,I}}, VK_I) \gets \mathsf{ML\text{-}DSA\text{-}44.KeyGen}()$
\State \textbf{At DN-AAA:}\ \ $(sk_{\mathsf{B}}, pk_{\mathsf{B}}) \gets \XWING.\mathsf{KeyGen}()$;\ \ $(sk_{\mathsf{SIG,R}}, VK_R) \gets \mathsf{ML\text{-}DSA\text{-}44.KeyGen}()$
\State \Return $(pk_{\mathsf{A}}, sk_{\mathsf{A}}, sk_{\mathsf{SIG,I}}, VK_I),\ (pk_{\mathsf{B}}, sk_{\mathsf{B}}, sk_{\mathsf{SIG,R}}, VK_R)$
\end{algorithmic}
}
\end{algorithm}

\subsection{Handshake}
Figure~\ref{fig:proto-edhoc} shows the exchange inside the 3GPP secondary-authentication flow, with the SMF as EAP authenticator and the DN-AAA as EAP server reached over RADIUS.

\textbf{Message~1} (Algorithm~\ref{alg:message1}). The UE generates its next key pair, announces $\mathit{Npk}_{\mathsf{A}}$ in $\mathit{EAD}_1$, encapsulates to the DN-AAA's current one-time key $pk_B$, and encrypts \texttt{Plaintext1}, including $\mathit{ID\_CRED}_I$, under $K_1$ derived from $ss_B$. It sends $\mathit{KeyID}_{\mathsf{B}} = H(pk_B)$ in the clear, so that the DN-AAA can select $sk_B$ before decryption, and binds $\mathit{KeyID}_{\mathsf{B}}$ and $ct_B$ to the message as AEAD associated data $AAD_1$ and through $TH_1 = H(pk_B, ct_B)$. As $K_1$ depends only on $ss_B$, $\mathit{ID\_CRED}_I$ is exposed only if the current $sk_B$ is compromised before the run.

\begin{algorithm}[H]
\caption{Construction of \texttt{Message1} (Initiator)}
\label{alg:message1}
{\footnotesize
\begin{algorithmic}[1]
\Require $pk_{\mathsf{B}} \text{ (current one-time public key of the DN-AAA)}$
\Ensure $\mathsf{Message1}$
\State $(\mathit{Nsk}_{\mathsf{A}}, \mathit{Npk}_{\mathsf{A}}) \gets \XWING.\mathsf{KeyGen}()$;\ \ $\mathsf{EAD}_1 \gets \mathit{Npk}_{\mathsf{A}}$ \Comment{next key of UE}
\State $(ss_{\mathsf{B}}, ct_{\mathsf{B}}) \gets \XWING.\mathsf{Encaps}(pk_{\mathsf{B}})$;\ \ $\mathit{KeyID}_{\mathsf{B}} \gets H(pk_{\mathsf{B}})$ \Comment{key identifier}
\State $\mathsf{Plaintext1} \gets (\mathsf{Method}, \mathsf{Suites}_I, \mathit{ID\_CRED}_I, C_I, \mathsf{EAD}_1)$
\State $TH_1 \gets H(pk_{\mathsf{B}}, ct_{\mathsf{B}})$
\State $PRK_{1e} \gets \mathsf{HKDF\text{-}Extract}(TH_1, ss_{\mathsf{B}})$
\State $K_1 \gets \mathsf{HKDF\text{-}Expand}(PRK_{1e}, TH_1)$
\State $AAD_1 \gets \mathsf{Encode}(\mathit{KeyID}_{\mathsf{B}}, ct_{\mathsf{B}})$
\State $\mathsf{Message1} \gets \big(\mathit{KeyID}_{\mathsf{B}},\ ct_{\mathsf{B}},\ \mathsf{AEAD.Enc}(K_1, AAD_1, \mathsf{Plaintext1})\big)$
\State \Return $\mathsf{Message1}$
\end{algorithmic}
}
\end{algorithm}

\textbf{Message~2} (Algorithm~\ref{alg:message2}). The DN-AAA selects the record by $\mathit{KeyID}_{\mathsf{B}}$, checks $\mathit{KeyID}_{\mathsf{B}} = H(pk_B)$ before decapsulating, opens \texttt{Plaintext1} with $AAD_1$, checks that $\mathit{ID\_CRED}_I$ belongs to that record, announces $\mathit{Npk}_{\mathsf{B}}$ in $\mathit{EAD}_2$, and encapsulates to $pk_A$; $ss_A$ keys \texttt{Plaintext2}, so only the holder of $sk_A$ reads the Responder's identity. It signs $TH_2\,\|\,\mathit{ID\_CRED}_R\,\|\,\mathit{MAC}_2$ with a key independent of $sk_B$, which makes Responder authentication KCI-resistant.

\begin{algorithm}[H]

Once secondary authentication succeeds, the UE and the DN-AAA share an identical EMSK. \subsection{Key Synchronization and Recovery}
\label{sec:sync}
Rotation changes state at both ends, so the order of the durable writes is fixed. The UE writes $\mathsf{NEXT} = (\mathit{Nsk}_{\mathsf{A}}, \mathit{Npk}_{\mathsf{A}}, \mathit{Npk}_{\mathsf{B}})$ before sending \texttt{Message3}; the DN-AAA commits its new record after verifying \texttt{Message3} and before sending \texttt{Message4}, then zeroes the old $sk_{\mathsf{B}}$, so it keeps no grace key; and the UE promotes $\mathsf{NEXT}$ only after verifying \texttt{Message4}, the protected success indication that EAP-EDHOC mandates~\cite{EAPEDHOC}. A UE holding $\mathsf{NEXT}$ starts its next run with it. If \texttt{Message4} or EAP-Success was lost, the DN-AAA has committed and the run succeeds; if \texttt{Message3} was lost, the DN-AAA cannot open \texttt{Plaintext1} and answers with an EAP-Failure, and the UE retries once with its old keys. A timeout never triggers this fallback, and the UE keeps $\mathsf{NEXT}$ until a run completes, so a forged, unauthenticated EAP-Failure can only delay it, and no case requires re-provisioning. Forward secrecy holds on every path: the session key needs both $ss_{\mathsf{A}}$ and $ss_{\mathsf{B}}$, and the DN-AAA erases its old $sk_{\mathsf{B}}$ when it accepts a run, so a later compromise cannot recover an accepted session even while the UE still holds its old $sk_{\mathsf{A}}$, as a dedicated ProVerif model confirms (Section~\ref{sec:formalverif}); such a retained key exposes at most that run's \texttt{Message2} content.

\subsection{Symmetry Analysis of the Design}
\label{sec:symmetry}
We call a protocol \emph{role-symmetric} if exchanging the Initiator and the Responder maps each party's cryptographic obligations onto those of the other. Table~\ref{tab:symmetry} shows that the proposal satisfies this in four respects: (i) two encapsulations, $ct_B$ in \texttt{Message1} and $ct_A$ in \texttt{Message2}, each feed the key schedule and key the message that delivers them, reproducing with a KEM the two-sided contribution of static Diffie--Hellman; (ii) each party signs its own transcript hash with a detached ML-DSA-44 key that the peer verifies as a mandatory gate, so, unlike the mirror-image methods T1/T2, KCI resistance holds in both directions; (iii) both parties rotate and erase their static keys, announced in $\mathit{EAD}_1$/$\mathit{EAD}_2$, which yields forward secrecy (R\ref{req:fs}) and post-compromise security (R\ref{req:pcs}) without an ephemeral key pair; and (iv) $\mathit{MAC}_2$ and $\mathit{MAC}_3$ give mutual key confirmation and identical MSK/EMSK. Three asymmetries are intentional. $\mathit{ID\_CRED}_I$ is protected only under the Responder's current one-time key (R\ref{req:idconceal}). Only \texttt{Message1} carries a key identifier, $\mathit{KeyID}_{\mathsf{B}}$, because only the DN-AAA serves many peers; since $pk_{\mathsf{B}}$ is one-time, $\mathit{KeyID}_{\mathsf{B}}$ changes after every completed run, and the outer EAP identity is an anonymous NAI~\cite{RFC7542}, as recommended for EAP-EDHOC~\cite{EAPEDHOC}. And \texttt{Message2} and \texttt{Message3} carry the signatures, although the bytes per direction balance ($6{,}146$~B from the UE, $6{,}113$~B from the DN-AAA).

\section{Formal Security Verification Using ProVerif}
\label{sec:formalverif}

We analyse the protocol with ProVerif~\cite{blanchet2001proverif,blanchet2016automated} in the Dolev--Yao model~\cite{DolevYao1983,dolev1983security}, following prior EDHOC analyses~\cite{JKK+23,NSB21,KDL+21,Fer24,cremers2017symbolic} and ISO/IEC~29128~\cite{ISO29128}. The verification targets nine requirements:
\begin{enumerate}[label=R\arabic*,ref=\arabic*,leftmargin=2.6em]
\item \label{req:mutualauth} \textbf{Mutual authentication}: each party is injectively authenticated to the other (agreement on the transcript).
\item \label{req:idconceal} \textbf{Identity concealment}: the persistent identities $\mathit{ID\_CRED}_I$ and $\mathit{ID\_CRED}_R$ are not learned by the adversary.
\item \label{req:confidentiality} \textbf{Confidentiality}: application data and session keys remain secret.
\item \label{req:keyexchange} \textbf{Secure key exchange}: MSK/EMSK are secret and agreed.
\item \label{req:fs} \textbf{Forward secrecy}: past session keys remain secret when the long-term state held after the session (signing keys and current static keys) leaks.
\item \label{req:pcs} \textbf{Post-compromise security}: after a static key is compromised, security is restored once the rotated $\mathit{Npk}_{\mathsf{A}}/\mathit{Npk}_{\mathsf{B}}$ is in use.
\item \label{req:aead} \textbf{AEAD protection} (Authenticated Encryption with Associated Data): plaintexts are integrity- and confidentiality-protected.
\item \label{req:qr} \textbf{Quantum resilience}: security holds against an adversary that can solve discrete logarithms, i.e., when X25519 and Ed25519 are broken (modelled by a quantum oracle).
\item \label{req:kci} \textbf{KCI resistance}: compromise of a party's static KEM key does not allow impersonation of the peer.
\end{enumerate}

Table~\ref{tab:verification-query} maps the requirements to queries. We model seven variants, T0--T3, the proposal, and the two EAP-TLS baselines as certificate-authenticated TLS~1.3~\cite{RFC9846} in the EAP-TLS~1.3 profile~\cite{RFC9190}, each in three settings: \emph{classical}, where an active attacker learns all long-term keys in phase~1; \emph{quantum}, which adds an oracle, available in every phase, that returns X25519 discrete logarithms and Ed25519 signing keys, modelling Shor's algorithm against active attacks and recorded traffic, with no such oracle for ML-KEM-768 or ML-DSA-44; and \emph{KCI}, where one party's long-term keys are known from the start. X-Wing is modelled with separate halves, so the quantum setting checks the hybrid property rather than assuming it, and the DN-AAA retrieves its key from a table indexed by $\mathit{KeyID}_{\mathsf{B}}$, with $\mathit{KeyID}_{\mathsf{B}}$ and $ct_{\mathsf{B}}$ as associated data of \texttt{Message1}. A property is fully secure (\statusfull) if it holds in both settings and partial (\statuspartial) if it holds only classically. For the proposal, phase~1 leaks the state a device holds after the run (the rotated X-Wing keys and both signing keys); a key-rotation model checks post-compromise security, a negative control (\texttt{edhoc\_m4v4\_fs\_noerase.pv}, one session suffices) also leaks the unerased old keys, and a recovery model (\texttt{edhoc\_m4v4\_recovery.pv}) lets the UE keep its old $sk_{\mathsf{A}}$, as after a lost \texttt{Message4}. All models target ProVerif~2.05 and are publicly available~\cite{ProVerifSrc}.

\subsection{Testbed and Cryptographic Cost}
Experiments ran in an Ubuntu 24.04 LTS VM (16\,GB RAM, 12 vCPUs) on an Intel Core i9-14900K host, with Open5GS~2.7.2~\cite{Open5GS}, UERANSIM~3.2.7~\cite{UERANSIM}, and FreeRADIUS~3.2.6~\cite{FreeRADIUS} co-located over loopback, so the network figures are a lower bound. Figure~\ref{fig:testbed} shows the components we modified or added; code and scripts are public~\cite{ProVerifSrc}. The EDHOC methods use libsodium~\cite{libsodium}, mbedTLS~\cite{mbedtls}, and the PQClean~\cite{pqclean} ML-KEM-768 and ML-DSA-44. The EAP-TLS~1.3 baselines~\cite{RFC9190} use OpenSSL~3.0.13 (Classic) and OpenSSL~3.2.6 with liboqs~0.16~\cite{liboqs} and oqs-provider~0.12~\cite{openssl_oqs} (Hybrid PQC: X25519MLKEM768~\cite{RFC10024} with ML-DSA-44 certificates~\cite{RFC9881,MLDSATLS}, checked at run time); OpenSSL implements RFC~8446, which RFC~9846~\cite{RFC9846} obsoletes compatibly and which forbids key-share reuse, so every handshake generates fresh shares. We measure on two paths. A RADIUS benchmark client, acting as EAP peer and RADIUS client (RFC~2865/3579~\cite{RFC2865,RFC3579}) against the same FreeRADIUS responder, compares all seven methods, including EAP-TLS, for which UERANSIM has no peer. The proposal also runs through the full path UE $\to$ gNB $\to$ AMF $\to$ SMF $\to$ UPF $\to$ FreeRADIUS (Section~\ref{sec:fullstack}), for which we enabled \texttt{SCTP\_NODELAY} on UERANSIM's NGAP socket, as Open5GS does, since Nagle's algorithm otherwise added about $160$~ms to every PDU session after the first. Table~\ref{tab:opcount} counts the operations of each party, with every key generation inside the handshake. The proposal costs $0.985$~ms, split evenly ($0.492$~ms per party) because both run mirror-image operations, against $0.894$~ms for EAP-TLS Hybrid PQC, which is why its computation bar in Figure~\ref{fig:handshake_computation_grouped} (left) is the highest. Both spend $0.566$~ms on two ML-DSA-44 signatures and verifications, and EAP-TLS adds $0.119$~ms of certificate checks, but the proposal performs six key generations against three: besides the share inside each X-Wing encapsulation, each party generates its next one-time X-Wing key pair for rotation ($0.116$~ms), and its encapsulation in each direction adds $0.094$~ms of key exchange. In process, with key schedule, AEAD, and serialisation, the two parties spend $1.131$~ms. In Figure~\ref{fig:handshake_computation_grouped} (right), ``Initiator'' is the UE's local processing and ``Responder'' the time it waits for replies, including the RADIUS round-trips and the DN-AAA's key storage.

\subsection{End-to-End Latency, Message Size, and Framing}
Over the RADIUS path ($200$ loss-free handshakes per method), the proposal completes in $6.383$~ms on average (median $6.284$~ms), against $8.273$~ms ($7.847$~ms) for EAP-TLS Hybrid PQC measured alternately in the same session, a median difference of $1.563$~ms (bootstrap $95\%$ interval $[1.436, 1.707]$~ms). In an earlier session, EAP-TLS Classic took $3.483$~ms ($3.101$~ms) and Methods 0--3 $0.996$--$1.277$~ms ($0.954$--$1.017$~ms; $1.021$--$1.039$~ms over pooled runs of $10{,}000$); as absolute times vary across sessions of our VM, we compare methods only within one session. The differences stem from transport, not computation (Figure~\ref{fig:communication_breakdown_methods}).

 Each X-Wing element adds $1.1$--$1.2$~KB and each ML-DSA-44 signature $2.4$~KB, so \texttt{Message1} ($2{,}390$~B, including the $32$-byte $\mathit{KeyID}_{\mathsf{B}}$), \texttt{Message2} ($6{,}097$~B), and \texttt{Message3} ($3{,}756$~B) split into $3$, $7$, and $4$ EAP fragments of 253-byte RADIUS attributes~\cite{RFC3579}, while \texttt{Message4} ($16$~B) fits in one: $12{,}259$~B in $15$ round-trips, balanced between the UE ($6{,}146$~B) and the DN-AAA ($6{,}113$~B), against $25{,}195$~B in $28$ for EAP-TLS Hybrid PQC, which carries ML-DSA-44 inside X.509 chains, and $2{,}478$~B in $6$ for EAP-TLS Classic. Each RADIUS round-trip costs about $0.3$~ms on loopback for both protocols, so the $13$ round-trips the proposal saves outweigh its $0.09$~ms of extra computation and its two durable writes, by a margin that grows with the SMF--DN-AAA round-trip time (RTT): a linear projection $T_{\mathrm{loopback}} + n_{\mathrm{RT}}\cdot\mathrm{RTT}$ gives $156$ against $288$~ms at $10$~ms. The two \texttt{fdatasync} calls on the critical path, the UE's write of $\mathsf{NEXT}$ and the DN-AAA's commit, cost $1.10$~ms against a \texttt{tmpfs} reference (bootstrap $95\%$ interval $[1.04, 1.15]$~ms; $0.53$~ms for the UE and $0.61$~ms for the DN-AAA), down from $7.9$~ms when each key had its own file. The DN-AAA keeps its $\mathit{KeyID}_{\mathsf{B}}$ index in memory and rebuilds it from the record slots at start-up ($0.46$~s for $10{,}000$ records with a warm page cache), so the lookup adds no write to the critical path. At the classical level, Methods 0--3 compute slightly less than EAP-TLS Classic ($0.182$--$0.202$ vs.\ $0.241$~ms), send $8$--$13\times$ fewer bytes, and complete $3.0$--$3.3\times$ sooner in the median. Cross-checks against pyca/cryptography confirmed all standard sizes.

\subsection{Full 5G Core Path}\label{sec:fullstack}
To confirm operation over a complete 5G core, we ran the proposal through UERANSIM and Open5GS with microsecond timestamps in the UE, the SMF, the UPF relay, and the DN-AAA. The SMF runs secondary authentication as step~6 of PDU session establishment~\cite{TS23502}, before policy association, UPF selection, and N4 setup: the UE answers the EAP-Request/Identity with the anonymous NAI \texttt{@edhoc.internet}, and neither its SUPI nor a DN-specific identity appears in the NAS or RADIUS messages, EAP-Success travels in the PDU Session Establishment Accept, and an EAP-Failure in a Reject with cause \#29~\cite{TS24501}, as a packet capture confirms. Three series of $100$ PDU sessions with secondary authentication alternated with three without it, each after five discarded warm-up sessions. All $300$ sessions were accepted with EAP-Success, with matching MSKs, rotated keys, and the sizes and $15$ round-trips of the RADIUS path. Table~\ref{tab:fullstack} gives medians with bootstrap CIs ($4000$ resamples). The added time is Request to Accept with minus without secondary authentication; the time at the UE runs from the first PDU Session Authentication Command to the Accept, so its 5G core row includes the policy, UPF, and N4 steps after the Access-Accept (about $5$~ms), which also occur without it. Secondary authentication adds $76$~ms to PDU session establishment ($21$ vs.\ $97$~ms), dominated by 5G core transport at about $4.6$~ms per NAS round-trip, so each round-trip the proposal saves weighs more here than on the RADIUS segment. The DN-AAA takes $5.0$~ms from the UPF relay, against $4.8$~ms seen by the benchmark client with the core running idle, and the relay adds $2.7$~ms for the SMF--UPF hop and $0.8$~ms for RADIUS processing. The UE's write of $\mathsf{NEXT}$ takes longer here than on the RADIUS path because it is the first \texttt{fdatasync} after the disk has been idle between sessions, a cost of our VM's disk that a probe without the protocol reproduces. Dropping \texttt{Message3} or \texttt{Message4} once at the relay ($10$ runs each) reproduced the recovery of Section~\ref{sec:sync}: the session with the drop was rejected without an EAP-Failure, so the UE kept its keys; after a lost \texttt{Message3} the next session was rejected with an EAP-Failure and the following one succeeded on the old keys (median $1.46$~s, including the $1$~s \texttt{reject\_delay} of FreeRADIUS); after a lost \texttt{Message4} the next session succeeded on $\mathsf{NEXT}$ ($101$~ms). No run desynchronised or required re-provisioning.

\subsection{Behaviour under Packet Loss}
Figures~\ref{fig:loss_mean} and~\ref{fig:loss_tail} show behaviour under emulated application-level loss with EAP-style retransmission (RTO 40~ms, up to $6$ retransmissions, $120$ trials per cell), measured before the $\mathit{KeyID}_{\mathsf{B}}$ field was added; the round-trip count, which drives the loss behaviour, is unchanged at $15$. Loss behaviour follows the round-trip count: if a round-trip succeeds with probability $p=(1-L)^2$ and an exchange fails after $7$ attempts, a handshake succeeds with probability $(1-(1-p)^7)^{n_{\mathrm{RT}}}$, which at $30\%$ loss predicts $87.4\%$ for the proposal and $77.7\%$ for EAP-TLS Hybrid PQC against the measured $93.3\%$ and $79.2\%$ (Wilson $95\%$ intervals $[87.4, 96.6]\%$ and $[71.1, 85.5]\%$; Fisher's exact test $p=0.002$, while up to $20\%$ loss the rates do not differ, $p=1.0$). Methods 0--3 keep $100\%$ up to $10\%$ loss and $96.7$--$98.3\%$ at $30\%$, as does EAP-TLS Classic ($96.7\%$). Within each security level the EAP-EDHOC variant degrades less: at $30\%$ loss Methods 0--3 average $144$--$165$~ms against $298$~ms for EAP-TLS Classic, and the proposal $713$~ms against $1{,}357$~ms, and the proposal has the lower mean latency of the hybrid pair at every loss level ($21.2$ vs.\ $41.6$~ms at $1\%$). Fragmentation, not computation, is the main scalability concern.

\subsection{EMSK Key-Bootstrapping Cost}
\label{sec:perf-bootstrap}
The bootstrapping chain is cheap (Figure~\ref{fig:bootstrap_cost}): its primitives cost $0.0012$--$0.0076$~ms, and of the $0.418$~ms loss-free end-to-end bootstrap only $0.034$~ms is key derivation, the rest being the AAA$\to$AS and UE$\to$AS network legs. A single core sustains $194{,}481$ sessions/s at the AAA and $106{,}182$ at the AS (Figure~\ref{fig:bootstrap_scale}a), and at $6.5\%$ of the handshake, bootstrapping is at least $4{,}700\times$ faster than a $2$--$10$~s manual OAuth~2.0 login (Figure~\ref{fig:bootstrap_scale}b). The label \texttt{"dsrk@ietf.org"} is reserved by RFC~5295, whereas \texttt{"oscore-bootstrap@<specorg>"} is a proposed private-use label; distinct labels on the same $\mathsf{Expand}$/$\mathsf{Extract}$ function give cryptographic separation, and $\mathit{id\_context}$ separates OSCORE sessions to one AS. RFC~5295 defines no DSRK transport; we meet the integrity, replay-protection, and key-wrapping requirements of RFC~5749~\cite{RFC5749} with mutual TLS~1.3 between the DN-AAA and the AS.

\section{Discussion}
\label{sec:discussion}

\textbf{Symmetric guarantees, asymmetric costs.} The protocol is role-symmetric in security, with independent signatures, KCI resistance, and key rotation on both sides, and balanced in computation ($0.492$~ms per party) and traffic ($6{,}146$ vs.\ $6{,}113$~B), but its cost is asymmetric: computation is about $15\%$ of the $6.383$~ms handshake, and most of the rest is fragmentation over $15$ round-trips. The extra computation against EAP-TLS Hybrid PQC is the price of symmetric rotation: both parties receive an encapsulation and must rotate, so key generation costs twice as much ($0.167$ vs.\ $0.084$~ms; Table~\ref{tab:opcount}). Faster primitives would thus barely change latency, whereas a larger EAP fragment size and RADIUS attribute budget where the operator controls both ends, a larger MTU on the SMF--UPF--DN-AAA segment, or more compact PQC signatures would cut transport without touching the verified logic.

\textbf{Design choices.} A signature-free KEM method~\cite{fraile2025reinventing,pocero} would save the ML-DSA-44 sign/verify cost ($0.223$/$0.060$~ms) but lose the detached signature that gives KCI resistance independent of the KEM key, and with it the explicit-authentication symmetry. Unlike Hybrid-EDHOC~\cite{SIK+25}, we keep \texttt{Message4}: it carries no key material but is the protected success indication that EAP-EDHOC mandates~\cite{EAPEDHOC} and the point at which the UE switches keys, for one $16$-byte fragment.

\textbf{Threats to validity.} The single-VM loopback figures are lower bounds, and the full path includes UERANSIM's simulated radio; loss is emulated at the application layer; and we do not rank Methods 0--3, whose medians differ by only $18$~\textmu s. The analysis is symbolic, with a discrete-log oracle for the quantum adversary; a diff-equivalence model of unlinkability across rotated runs did not terminate within our memory limit, so we do not claim that property; and the AAA$\to$AS DSRK channel rests on a co-location/mTLS assumption analogous to ERP~\cite{RFC6696}. Forward secrecy rests on erasure, which the recovery rules preserve on every modelled and tested path, and post-compromise security heals from the first run after a compromise. Re-authentication and handover are not evaluated.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Conclusions}
\label{sec:conclusion}
We proposed a role-symmetric hybrid post-quantum EAP-EDHOC protocol for 5G secondary authentication, in which two opposite X-Wing encapsulations to one-time static keys, detached ML-DSA-44 signatures, and a two-sided key rotation with erasure give forward secrecy and post-compromise security without an ephemeral key pair. ProVerif shows that only the proposal combines quantum resilience, KCI resistance, forward secrecy, and post-compromise security, with identity concealment of $\mathit{ID\_CRED}_I$ unless the Responder's current one-time key is compromised before the run, and a lost message never forces re-provisioning. On Open5GS, UERANSIM, and FreeRADIUS the handshake exchanges $12{,}259$~B, split evenly between the directions, and completes in $6.383$~ms against $8.273$~ms for EAP-TLS Hybrid PQC: it computes slightly more ($0.985$ vs.\ $0.894$~ms) but needs about half the round-trips ($15$ vs.\ $28$), and inside PDU session establishment on the full 5G core it adds $76$~ms, mostly NAS transport. The exported EMSK bootstraps OSCORE keys for login-free application-server access. Future work covers compact PQC parameter sets, fragment-size and MTU tuning, mobility and handover, a computational proof, and IANA registration of the OSCORE-bootstrap label.
